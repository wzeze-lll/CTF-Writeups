# tuling_complete：MOV 混淆里优先找比较数据（学习版 WP）

> [!important] 证据边界
> 本文依据用户提供的静态分析记录整理。下方“常量 → key → flag 前缀”的 Python 计算已独立复算；但原笔记编写时尚未取得原始 `tuling_complete` ELF；仓库现有附件是 32 位 ELF，因此 `.data` 虚拟地址到文件偏移、`memcmp` 调用位置和程序实际接受该输入，仍是待原附件验证的项目。不要把本页的 `0x5030` 当成任何 i386 ELF 的通用偏移。

| 字节变换 | 十个 16 位常量 → 小端字节 → 相邻 XOR key | 下方脚本已复算 |

这道题的学习重点不是逐条还原所有 `mov`，而是把最终校验缩成：

```text
输入的前 11 字节 ── XOR key ──> 目标密文前 11 字节
后 29 字节                     → 目标数据中直接可读
```

## 从常量到 key：为什么是小端序

静态记录中有十个 16 位常量：

```python
nums = [
    0x1234, 0x5678, 0xABCD, 0x1212, 0x2333,
    0x3389, 0x1122, 0x2222, 0x1A1B, 0xAABB,
]
```

x86 以小端序保存 16 位数，因此 `0x1234` 在内存里是 `34 12`，不是 `12 34`。连续展开后，脚本按下图的相邻字节 XOR 形成 11 字节 key：

```text
raw: 34 12 78 56 cd ab 12 12 33 23 89 33 22 11 22 22 1b 1a bb aa
key: 34 6a 9b b9 21 aa 11 33 39 a1 aa
```

第 2 个 key 字节为 `0x12 ^ 0x78 = 0x6a`；这就是“相邻字节 XOR”的意思。此处如果把整数按大端序展开，第一步就无法得到 `flag{`。

## 可直接运行的静态复算脚本

```python
from struct import pack

# 用户记录的 40 字节目标数据：前 11 字节是密文，后 29 字节可读。
enc = bytes.fromhex("52 06 fa de 5a de 59 02 4a 90 d9") + b"_c0mp1lEDBy_movfuscator_Ohno}"
nums = [
    0x1234, 0x5678, 0xABCD, 0x1212, 0x2333,
    0x3389, 0x1122, 0x2222, 0x1A1B, 0xAABB,
]

raw = b"".join(pack("<H", n) for n in nums)  # 每个 16 位常量按 x86 小端序展开
key = bytearray([raw[0]])
for i in range(1, 10):
    key.append(raw[2 * i - 1] ^ raw[2 * i])    # 相邻字节 XOR
key.append(raw[-1])

prefix = bytes(a ^ b for a, b in zip(enc[:11], key))
flag = prefix + enc[11:]

assert bytes(key) == bytes.fromhex("34 6a 9b b9 21 aa 11 33 39 a1 aa")
assert prefix == b"flag{tH1s1s"
assert len(enc) == len(flag) == 40
assert bytes(a ^ b for a, b in zip(flag[:11], key)) + flag[11:] == enc
print(flag.decode())
```

输出：

```text
flag{tH1s1s_c0mp1lEDBy_movfuscator_Ohno}
```

最后一个 `assert` 是正向验证：把复原出的前 11 字节再 XOR 同一把 key，应该重新得到原密文。它证明的是**这套静态字节公式自洽**，不证明原 ELF 的地址映射或运行时流程已经验证。

## 有附件后，如何正确读取目标数据

不要直接假设 `0x804e030 → 文件 0x5030`。先运行：

```bash
file ./tuling_complete
readelf -lW ./tuling_complete
readelf -x .data ./tuling_complete
```

在 `readelf -lW` 找到包含 `0x804e030` 的 `LOAD` 段，按下式求文件偏移：

```text
offset = 0x804e030 - p_vaddr + p_offset
```

确认偏移后，才使用下面的读取段：

```python
from pathlib import Path

DATA_FILE_OFFSET = 0x5030  # TODO：仅当上面的 LOAD 段换算确认后填写
enc = Path("tuling_complete").read_bytes()[DATA_FILE_OFFSET:DATA_FILE_OFFSET + 40]
assert len(enc) == 40
```

如果本地具备 i386 动态加载环境，再将最终 flag 按程序输入协议送回去，并记录真实成功提示。若缺少 32 位 loader/libc，先保留 `STATIC_RECONSTRUCTED_AND_SCRIPT_VERIFIED` 状态，不升级为“已本地复现”。

## 看到什么想到什么

| 现象 | 第一反应 |
|---|---|
| 主逻辑几乎全是 `mov` | 识别 MOV 混淆；转而找输入、常量和最终比较 |
| `memcmp(a,b,n)` | 断在调用点/函数入口，拿到真实 `a`、`b`、`n` |
| 16 位常量写入 | 先按 `<H` 小端序展开，不要直接按十六进制视觉顺序抄 |
| 解出 `flag{` 前缀 | 再做正向重编码验证，而不是只相信“看起来像 flag” |
| 虚拟地址写进 Python 切片 | 先查 `PT_LOAD`，将 `vaddr` 换成文件偏移 |
